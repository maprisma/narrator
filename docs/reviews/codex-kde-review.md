Found five bugs in the new code, plus an inherited authorization weakness relevant to the new KDE permissions.

1. **[P1] Area screenshots use the wrong D-Bus signature.** [desktop/src/kde.rs:326](/mnt/Data/Projects/maprisma-narrator/desktop/src/kde.rs:326) casts width and height to `u32`, producing `iiuua{sv}h`. KWin requires `iiiia{sv}h`. Every `CaptureArea` call therefore fails, including area reading and the area part of `--self-test`. Keep both dimensions as `i32`. See [KWin’s implementation](https://github.com/KDE/kwin/blob/master/src/plugins/screenshot/screenshotdbusinterface2.cpp).

2. **[P1] A surviving watcher is never replaced after a helper crash.** [desktop/src/kde.rs:213](/mnt/Data/Projects/maprisma-narrator/desktop/src/kde.rs:213) starts the watcher only when its fixed name is absent. After `SIGKILL` or a crash, the old script remains loaded and still targets the previous helper’s unique bus name. The replacement helper consequently receives only ten-second refreshes. Moving, minimizing or changing focus between refreshes leaves stale geometry and visibility; a page key can even reach another window because the final focus check uses that stale snapshot. Replace the watcher unconditionally when each helper starts.

3. **[P2] Screenshot timeouts leave blocking pipe readers alive.** [desktop/src/kde.rs:295](/mnt/Data/Projects/maprisma-narrator/desktop/src/kde.rs:295), [desktop/src/kde.rs:341](/mnt/Data/Projects/maprisma-narrator/desktop/src/kde.rs:341). Timing out or dropping a `spawn_blocking` handle does not stop its `read_to_end`. If KWin stalls while retaining the passed write descriptor, the call returns but its reader thread remains blocked. Repeated attempts accumulate threads; terminating the helper can then hang while Tokio shuts down its blocking pool, preventing supervision from restarting it. Use a cancellable/nonblocking pipe reader and explicitly close it on timeout.

4. **[P2] Setup progress never refreshes while the tray menu stays open.** [tray/src/main.rs:391](/mnt/Data/Projects/maprisma-narrator/tray/src/main.rs:391). After choosing setup, the stored response contains `setup_busy=true`. Subsequent polls merge only `enabled`, `paused` and `status`; they never update setup progress, readiness or errors. Once setup finishes, the open menu still shows setup running and keeps Start disabled. Closing and reopening triggers `AboutToShow` and repairs the state. Poll full status while setup is busy, as the COSMIC applet does while its popup is open.

5. **[P2] Letter keys assume a US keyboard layout.** [desktop/src/kde.rs:424](/mnt/Data/Projects/maprisma-narrator/desktop/src/kde.rs:424). The interface accepts keysyms, but `n`, `p` and `b` become fixed physical evdev positions. With US Dvorak active, requesting `n` produces `b`, so a viewer using `n` for next page receives the wrong command. Resolve letter keysyms through the active keymap before injecting them.

The security issue is **pre-existing**, rather than introduced by the extraction: [desktop/src/main.rs:122](/mnt/Data/Projects/maprisma-narrator/desktop/src/main.rs:122) authenticates callers using mutable command-line arguments. A same-user process can include the installed helper path in its argv and spawn real `busctl`, satisfying both checks without running the installed reader helper. While reading is enabled, it can request screenshots and keys through the newly authorized KDE executable. This does not enforce the stated “only the installed reader” boundary.

The shared COSMIC control module is behavior-identical on inspection; its differences are visibility, formatting and equivalent block expressions. I found no concrete additional defect in the tray signatures, `LayoutUpdated`, Event/EventGroup, registration logic, or installer quoting/path handling.

No files changed. The four existing compiled Rust tests passed; I did not rebuild or perform live Plasma validation.
